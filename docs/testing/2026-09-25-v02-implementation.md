- 北京平台客户端无自动重试、不跟随跳转、不持有 Cookie；HTML 校验页、限流、业务错误和明确未登录分开处理。目录界面支持重试、已加载医院搜索、分页与渠道切换时取消旧请求。

**尚未实现／验证：** 北京平台独立客户端正常认证、患者读取、医生详情动态请求构造、实际提交、同单核对和支付状态。北京 114／京通自动任务入口因此仍不可启用，未提供虚构的认证成功或提交结果。v0.1 佑安真实入口继续保留。

## 原生请求实测

一次宿主网络只读 `POST https://www.114yygh.com/jtjk/mobile-service/hospital/list`，使用公开业务脚本中的 `Request-Source: WE_CHAT` 和已观察的目录字段；没有用户凭据，没有代理或 CA。

结果为 **HTTP 202、`text/html; charset=utf-8`**，不是医院 JSON，不能认定目录接入成功。仅保存[脱敏结果及回包摘要](evidence/v0.2/native-query-probe.json)，未入库原始 HTML 或动态校验参数。未分析或仿造校验脚本，未登录、读取患者／订单、预约或付款。

官方业务脚本还确认 `WE_CHAT` 与 `JT_WECHAT` 是不同渠道值。普通查询适配层可以共享，但当前没有证据允许两个渠道互用会话。此前手机官方页面的两医院查询成功仍是页面观察证据，不是这次原生请求成功。

当前 `adb devices` 只有本轮创建的模拟器，没有 USB 手机。已向用户请求接回手机并停在已登录京通首页；后续继续正常认证及查询验证。不能以时间流逝推定用户已连接或授予真实预约权限。

## 中间失败与修复

1. 一次安装早于 AndroidTest 构建结束，新增测试类未进入当时安装包；等待构建完成后重新安装运行。
2. 旧医保流程测试复用已有演示订单日期，被正常防重复保护拦住；改用本机未使用的测试日期。未降低真实重复订单保护。
3. 并行服务通知测试固定等 1 秒，偶发早于通知更新；改成最多 3 秒条件等待，并在放号前确认两个任务，再验证停止一个不影响另一个。
4. 一次 debug 回归尚未结束就安装了 release，测试进程被安装打断；随后按完成回读后再换包的顺序重新运行。
5. release 隔离测试期望中缺少 v0.1 数据库存储时自动补全的连接 binding；补全合成 fixture，继续完整比较记录，不忽略任务／订单字段。
