# 挂号 App v0.1：需求与实现方向讨论稿

状态：用户要求先完成服务号真实流程验证；技术方案待评审，尚未开始 Android 实现。目标设备为华为 Mate 60 Pro，鸿蒙 4.2.0。首个医院为北京佑安医院。

## 已确认的需求

医院通常提前 X 天，在指定时间开放目标日期的号源。用户提前设置就诊人、科室、医生、目标就诊日期及放号时间，由 App 到点自动尝试预约，避免必须守着手机或忘记放号。App 切到后台或手机锁屏后也要执行；形成待支付订单后停止抢号并通知用户付款。

自动尝试围绕一次放号事件执行。最长运行时长可配置，默认 30 分钟，从放号时间开始计算；提前取得有效订单就提前结束。提前检查登录和设备条件的时间不计入该时长。X 天和放号时间是可填写、可核对的医院规则，不能假定所有科室始终相同。

用户原话：“提前设置好就诊人，要挂号的科室和医生，以及告诉你放号的时间，到时间你自动挂号，然后通知我去付款。”

UI 美化后置，可在数据与运行方案确定后使用 Pencil。用户最新明确：服务号接口锁号后，在手机微信“挂号结果查询”找到待支付订单并付款。2026-09-24 单笔验证已取得锁号成功、手机订单可见、医院已预约回查的证据；没有启用定时自动任务。

## 推荐的执行方式

| 方案 | 对本需求的适用性 | 取舍 |
| --- | --- | --- |
| 手机本地定时唤醒＋有通知的前台服务 | 推荐。等待期间保存任务，放号窗口内持续工作，满足锁屏与后台执行目标 | 不需要托管用户会话；需验证鸿蒙定时唤醒、后台管理和锁屏网络 |
| WorkManager 周期任务 | 可用于非精确的检查或恢复辅助，不用于放号执行主循环 | 官方周期任务最小间隔 15 分钟，执行时间也不是精确保证 |
| 云端定时执行 | 手机关机或离线时仍可执行，但超出当前需求 | 需要托管凭据、部署服务并维护通知链路，v0.1 暂不引入 |

建议以原生 Kotlin Android App 实现，手机接入微信服务号挂号接口；不使用 Google 服务作为必需依赖。具体 SDK、前台服务类型和电源权限按目标机实际兼容能力选择，不能从“鸿蒙 4.2.0”直接推断 Android API level。

## 一个预约任务包含什么

| 内容 | 行为 |
| --- | --- |
| 医院、渠道 | v0.1 固定佑安微信服务号；与互联网医院会话和订单分开 |
| 就诊人 | 选择已绑定的就诊人；任务执行前核对身份仍有效 |
| 科室、医生 | 精确匹配所选项；不自动替换其他医生或科室 |
| 目标就诊日期 | 与放号日期分别保存；按“提前 X 天”推算时展示最终日期供核对 |
| 就医方式 | 展示服务号的“是否专程来京就医”等条件，由用户启用任务时核对；不把测试默认值用于所有任务 |
| 可接受时段 | 可选择上午、下午或具体时间范围；不填时展示“当天任意可预约时段” |
| 费用上限 | 启用前明确可接受上限；费用超出时不提交 |
| 放号时间 | 记录北京时间的明确日期和时刻，并展示倒计时 |
| 最长运行时长 | 用户可配置正整数分钟，默认 30；截止时间为放号时间加该时长 |

建议 v0.1 同一时间只执行一个任务，每个任务只取得一个符合条件的预约。多医生候选排序、并行多任务和自动付款不纳入本版方案；这是待评审的范围建议。

## 执行与停止规则

1. 保存任务时检查正常登录、就诊人、条件完整性、通知与定时运行权限。通过后显示“已就绪”，明确计划开始与截止时间。
2. 放号前执行准备检查；若登录已失效，提前通知用户重新登录。准备检查也受系统调度限制，不能保证在每次唤醒前均成功执行。
3. 定时唤醒后启动前台服务，通知栏持续展示任务阶段与停止入口。放号前只准备，放号时发起首轮查询。
4. 用服务端返回的医生、日期、时段、余号和费用匹配条件。初步建议查询间隔不短于 5 秒、每次只有一个请求在途；具体节奏受医院限制和真机测试约束。限流时退避，不并发刷接口。
5. 匹配后核对任务条件及服务号功能校验，调用一次 `lockRegis`。不跨医生、日期或费用自动降级，收到接受处理不等于锁号完成。
6. 通过 `queryRegisStat` 核对异步结果，取得订单号后用 `getRegisList` 精确匹配。状态为 1 且需要付款时停止查号并通知；后续状态 2 显示已预约。零元、候补或未知状态分别处理，不混作普通付费预约。
7. 达到配置的截止时间后，不发起新的查询或提交。在截止前已发出的提交若结果未明，仍需完成有限的结果核对并提示用户，不能假装它没有发生。
8. 用户停止后立即阻止新请求；已经发出的锁号不能撤回，仍核对它是否形成订单。停止任务不等于自动取消医院预约。

## 提交异常与恢复

查询失败可以有限退避重试。锁号请求超时、连接断开或进程退出时，必须进入“结果待核对”，不能直接重新锁号。

有订单号时从服务号预约列表精确匹配，本次已验证成功。无订单号时按患者、日期、医生、时段和提交时间关联的恢复策略尚未实测；列表暂时为空不代表请求一定失败。无法唯一确认时暂停任务并通知用户核对，不继续自动提交。

任务状态、条件和提交尝试记录持久化；运行时长和订单付款剩余时间分别计算。重启恢复时先检查截止时间与是否有未确认的提交。登录缺失、权限被撤销或结果未明时恢复为需要处理的状态，不悄悄提交。

## 通知与付款

使用手机本地通知：任务执行中提供停止入口；待付款、未挂上和需处理异常提供明确结果。锁屏默认隐藏就诊人姓名等个人细节，点入 App 后查看医生、日期、金额和订单。

待付款通知以服务号订单状态和 `invalidtime` 为准；通知应显示实际可确认的截止时间，不能沿用任务运行时长。支付由用户操作。

付款交接采用“通知 → 手机微信服务号 → 挂号结果查询 → 缴费”，用户完成支付后回查同一订单。23:33 的单笔服务号锁号已在手机端可见，后端随后返回“已预约”；该订单支付窗口约 30 分钟，不能写死。此前互联网医院网页订单约 5 分钟且未出现在服务号结果列表，因此不依赖跨渠道订单同步。第三方 App 的微信页面直达与回跳仍未验证，v0.1 可先给出明确人工入口。


## 数据模块与本机保存

- 任务执行模块：管理定时唤醒、条件匹配、截止时间、单次提交和异常恢复；页面只发出创建、启用、停止等用户意图。
- 医院接入模块：集中处理医院请求头、会话、响应解析、号源与订单语义。读取响应保留原始状态码，未知状态不当成成功或无号。
- 本地状态模块：保存任务、必要的提交恢复记录及通知结果。会话凭据使用 Android Keystore 保护；认证方式按服务号初次授权实测再定。日志不包含票据和完整患者资料。
- 付款交接模块：处理已验证支付入口及返回后的订单回查，不把“打开了支付页面”当成支付成功。

先为一个医院建立清晰模块，不预建通用多医院平台。互联网医院研究证据继续保留，待后续确需第二个渠道时再抽象差异。

## 真机验收与目前证据

已验证：服务号已有会话、就诊人列表、科室排班、分时余号、单笔锁号、手机“挂号结果查询”订单可见，以及同一订单返回“已预约”。互联网医院独立短信登录与查询另有研究证据。未验证：服务号初次认证、会话自然失效恢复、独立支付流水、异常恢复和 Mate 60 Pro 真机后台行为。

开发验收需覆盖：提前设置后长时间锁屏到点唤醒、切后台、Wi-Fi 与移动网络切换、短时断网、通知与电源权限变化、进程被系统回收、重启后任务恢复、时钟修改，以及提交时断网后不重复预约。任务不能在用户强行停止 App、关机或无网络时承诺继续执行。

先以模拟医院响应验证提交状态机、截止规则和恢复行为，再在目标机验证真实认证与查询；真实提交和付款仅使用用户确认的实际就医条件完成一次受控验收。技术可行性不能替代真实就医授权。

Android 官方说明：

- [前台服务](https://developer.android.com/develop/background-work/services/fgs)：运行时需可见通知，但并不自动豁免所有省电限制。
- [Doze 与 App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)：锁屏深度空闲可能限制网络和唤醒锁，豁免也仅是部分豁免。
- [定时闹钟](https://developer.android.com/develop/background-work/services/alarms/schedule)：精确定时受系统版本和用户权限约束，重启或权限变化需重新检查。
- [后台启动前台服务限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)：存在用户请求的精确闹钟等例外，具体适用性需结合目标系统。
- [WorkManager 周期任务](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)：周期最短 15 分钟，不作准点抢号执行器。
