# 多医院连接与并行挂号任务

日期：2026-09-25。状态：隔离设计稿已完成，供评审；尚未实现多医院并行。用户已确认先完成隔离设计，第二家医院稍后确定，本轮不接入第二家医院。

## 需求与本轮修正

用户需要同时为多家医院设置挂号任务。连接 B 医院不应被 A 医院的待触发、执行中或结果待确认任务阻塞；演示任务也不参与医院连接保护。只有真正可能重复锁号或无法区分响应的提交才需要相互限制。

本轮已取消新增连接的任务状态门禁。每次导入创建新的会话实例和独立 Cookie 存储，已有任务继续引用原 `PatientRef`，不会因默认连接变化而改用新就诊人。连接仍受域名、链接格式、身份一致性和挂号功能核验约束。

当前真实适配器仅为佑安服务号。全局启用限制、执行器互斥、数据库单执行者和后台服务单 worker 尚待按本设计改造；不能仅删除前端限制就宣称支持并行。

## 连接与任务归属

- 医院使用稳定 `hospitalId`；接入来源使用 `providerId`，例如服务号、互联网医院或其他已验证平台。域名只是适配配置，不是跨渠道共享身份的依据。
- 连接保存医院、来源、该来源中的账户、已核验就诊人、会话版本和校验状态。个人资料与凭据仍本机加密。
- 任务创建时固定绑定医院、来源、就诊人、连接版本和就诊条件。后续用户查看或添加其他医院，只改变新建任务时的默认选择。
- 同一就诊人重新登录可生成新会话版本，但旧任务不悄悄替换凭据或身份。若需要迁移任务，必须验证医院/来源/账户/就诊人全部相同，再由用户明确选择；有未决提交的任务先保持原恢复上下文。
- 连接过期是该连接的状态，不能让其他医院或其他就诊人的连接变为失效。

### 数据模型

| 对象 | 关键字段 | 隔离规则 |
| --- | --- | --- |
| Hospital | `hospitalId`, 展示名 | 本地稳定标识，不依赖界面顺序或域名 |
| Provider | `providerId`, 允许域名、适配器、限频规则 | 支持一个平台覆盖多医院；服务号与互联网医院不是同一个来源 |
| Principal | `providerId`, `accountKey`, `patientKey` | 标识来自医院已验证响应，使用稳定本机密钥生成 HMAC 存储索引；不把姓名当唯一键，不输出明文身份 |
| Connection | `connectionId`, 医院/来源/Principal、`activeCredentialVersion`, 校验状态 | 一个逻辑连接可有多版凭据；校验按版本记录，过期事件不能覆盖新版本 |
| CredentialVersion | `connectionId`, `versionId`, 加密凭据及 Cookie | 每版独立存储；不把当前连接作为所有任务的隐式依赖 |
| Task | `taskId`, 医院/来源/Principal、`credentialVersionId`, 条件、时刻、截止时间 | 创建时快照绑定，不因切换界面或新增连接改写 |
| SubmissionAttempt | `attemptId`, `taskId`, 原凭据版本、基线、候选号源、`submissionScopeKey`, 状态 | 请求前持久化，回查只能认领与该尝试唯一匹配的结果 |

连接列表显示每家医院的所有已核验就诊人，不覆盖另一家医院的连接。默认选择只是用户偏好，任务与付款查询均按任务自身绑定路由。历史会话继续保留以支持订单查询；清理历史凭据属于独立数据生命周期功能，本次设计不自动删除。

### 重新登录与恢复

新增连接、重新授权和只读核验都不受未决提交阻塞。如果适配器初始化确实会改变同一医院账户的服务端“当前就诊人”，必须标明这种副作用：允许先保存新连接；影响正在提交的同一账户时，只将该有副作用的初始化步骤排队，不阻塞其他医院的连接。

旧任务凭据失效时，任务明确显示自己的失效状态。用户完成同一医院、来源、账户、就诊人的重新授权后：

- 尚未发出提交的任务：提供“更新此任务连接”，展示绑定身份，用户确认后只换凭据版本，重新核验条件；不重新计算放号时间，不自动启用。
- 已有未决提交或订单的任务：提供“用新连接核对本次结果”。确认身份完全相同后，仅给只读订单核对提供新凭据，保留原 `attemptId`、基线及冲突范围，不发新的锁号、付款初始化或取消请求。核对无法唯一关联时继续待处理。
- 身份或来源不相同：可保存为独立连接，但不得接管旧任务或旧订单。

这避免“必须先解决未决提交才能登录，而解决它又必须先登录”的循环，同时不把重新登录当成重新提交的许可。

## 执行与重复提交保护

不同医院可同时等待放号，且各自到点启动、停止、通知。持久化执行权防止同一任务被闹钟、重启恢复和人工入口重复执行。查询和提交分别控制并发与限频。

冲突保护由适配器给出准确作用范围：默认以医院、来源和真实账户/就诊身份区分，不能用随机会话实例 ID 代替账户，否则重新登录会绕过保护。若某平台的异步结果只按账户查询、覆盖该账户下多个医院或就诊人，提交/核对阶段必须使用该平台账户的共享锁；不同医院的独立查询仍可并行。当前佑安 `queryRegisStat` 只按 userId 查询，需要保留账户范围的结果关联保护。

一笔提交结果不明时，保留其尝试、基线订单、条件和恢复上下文；仅暂停同一冲突范围中的新提交。添加连接、浏览其他医院、独立范围的任务均可继续。不能将列表暂空解释为无订单。

### 冲突处理矩阵

| 情形 | 添加/核验连接 | 等待放号及查询 | 发出新提交 |
| --- | --- | --- | --- |
| A 未决，B 是独立医院后端 | 允许 | B 正常执行 | B 允许；A 保留原未决保护 |
| A、B 共用平台，但各有独立提交结果查询键 | 允许 | 按平台请求频率运行 | 各范围可独立提交 |
| A、B 共用同一平台账户，结果只有账户级接口 | 允许 | 独立查询可继续 | 同一账户提交/核对阶段串行；窗口内等待，截止后不补交 |
| 同一医院同一账户更换会话版本 | 允许 | 已有任务绑定不变 | 不能通过新版本绕过原冲突范围 |
| 演示任务与真实医院任务 | 允许 | 分开执行 | 演示仅调用模拟适配器，不持有真实范围锁 |

医院请求限频与结果关联锁是两个概念：适配器按接口契约选择来源、域名或账户级请求预算，遵守 Retry-After；不会通过增加连接数提高请求频率。提交去重锁只持有与结果归属相关的范围。所有任务均保留一次提交前的持久化记录和无透明重试约束。

### 调度与恢复顺序

1. 用户可启用多条任务；校验各任务自身的连接与条件，登记各自闹钟，不用“已有任意任务”阻止启用。
2. 到点后为 `taskId + generation` 取得数据库执行权；重复闹钟只会唤醒同一任务，不产生第二个 worker。
3. 查询满足条件后，在短数据库事务中取得 `submissionScopeKey` 执行权并写入提交尝试，再发请求。不能在网络请求期间持有数据库事务。
4. 遇到相同范围占用时，显示“等待同账户前一笔结果”，保留原截止时间；其他范围照常运行。
5. 成功或明确无号后按协议释放范围；不明确的尝试即使进程退出、运行窗口结束，也保留持久未决保护，不能仅靠锁超时自动解锁。
6. 重启时可恢复失去进程所有者的 worker，但先核对持久尝试，再决定查询/恢复；已提交任务不能回到全新锁号分支。

## Android 后台与存储

后台服务改为按任务管理多个 worker；新任务到达时不能被现有 worker 直接忽略。前台通知展示运行任务概况，每条结果独立送达，停止一个任务不停止其他任务。服务与 WakeLock 在最后一个工作完成后释放。现有铃声/振动完整播放的修复需要并行场景回归。

数据库迁移必须保留现有加密任务与未决提交。现有佑安记录补默认医院/来源标识；替换全局 `single_running_owner` 的同时增加每任务唯一执行权与冲突范围保护。迁移前后比较记录数量、原任务身份、订单和尝试内容；不清空数据库。

迁移计划采用 SQLite schema v2：保留 `tasks`，增加任务归属索引与 `submission_scopes`；在事务内替换全局执行者唯一索引，并回填现有佑安和 demo 归属。加密负载缺少新字段时有明确默认值。对已有未决提交先回填冲突范围，再允许新调度；无法确认账户归属的历史未决任务进入“身份待核对”，仍可添加连接，但不启用可能冲突的该平台新提交。

前台服务按任务 ID 维护 worker 集合，并发结束使用同一协调器更新引用计数和通知，避免一个 worker 的 `stopSelf()` 关闭其他工作。系统重新派发的 intent 每次都进入去重调度，不能因已有 worker 而直接丢弃。各任务截止时间不因排队或重启延长，成功通知按任务独立 ID 分发，汇总进度静默更新。锁屏、后台与异常恢复依旧在目标 Mate 60 Pro 上验收，未验收前不承诺设备保活可靠性。

### 实现变更位置

| 当前实现 | 后续变更 |
| --- | --- |
| `AppGraph` 的单一 PscClient 与全局启用门禁 | 注册适配器并按任务归属路由；启用不再以任意其他任务为障碍 |
| `SessionRepository.current-session` | 连接目录与各连接的凭据版本；全局当前值只用于 UI 默认选择 |
| `BookingEngine.runMutex` | 每任务执行去重，另设稳定身份的提交范围保护 |
| `BookingDatabase.single_running_owner` | 原位迁移为每任务 claim 和提交范围记录 |
| `BookingService.worker`、全局付款锁 | 多任务工作集合；付款协调按任务/订单范围进行 |
| 任务详情使用当前连接状态 | 按任务连接读取状态与身份，不随设置页选择变化 |

增加第二家真实适配器前，使用两个隔离的模拟医院以及一个共享账户结果接口的模拟平台验收并发、范围冲突和数据路由。后续真实适配仅替换模拟入口，不能省略对应协议和设备验收。

回滚需要区分代码与数据：迁移失败时整个事务回滚，保持 v1 可读；迁移成功后若已经产生新任务或订单，不直接安装不理解 v2 的旧包。应提供兼容 v2 数据的功能回滚版本，或在确认升级后无新业务数据时恢复升级前加密备份。备份只留本机，凭据不进入日志或版本库。

## UI

设置中的“医院连接”改为列表，每家医院独立显示就诊人、状态、最近校验时间和重新连接入口。新建任务先选医院/来源与就诊人，再选择科室/医生。任务卡和通知明确医院，避免同名科室、医生或付款订单混淆。

本轮只改现有连接错误提示及绑定规则；多医院 UI 可以先用虚构的医院 A/B 完成 Pencil 设计，不依赖确定第二家真实医院。

## 必须覆盖的验收

1. A 医院任务待触发时连接 B；A 的时间、凭据绑定和任务记录不变。
2. A、B 同时放号均触发；停止 A 不终止 B，不丢失到达服务的新任务。
3. A 提交超时，B 的独立任务继续；A 同一冲突范围不重复提交，重新导入也不能绕过。
4. 切换医院、同名就诊人、会话失效、不同支付方式均不串用凭据、订单或通知。
5. 从现有版本原位升级后数据完整；进程回收、重启、断网和锁屏期间各任务独立恢复。

当前连接修复的测试不替代上述多医院验收。实际第二家医院仍需验证入口、认证、放号/订单语义和支付接续；不能假设与佑安相同。
