日期：2026-09-25。状态：**设计稿已形成，待用户评审；本任务不进入开发。**

## 1. 设计结论

采用**统一挂号流程、平台适配器、医院规则配置**的结构。新增平台首选北京市预约挂号统一平台，以北京 114 官方移动渠道为首批协议核验对象，保留佑安微信服务号。114 官网公告确认网站预约渠道自 2023-12-08 关闭，不能再把桌面网站列为预约或认证实现路径。北京市政府 2026 年报道明确京通 App 是统一平台总入口，因此接入验证同时覆盖京通正常用户流程。只有证明协议和会话可复用后，京通才与 114 合用适配器。京医通的历史接口不作为新版本接入基线。

v0.2 的目标仍是用户提前设置条件，到放号时间自动尝试挂号，形成有效预约后停止并提示下一步。平台支持多个医院，并不意味着本 App 已支持目录里的全部医院。每个“平台＋医院＋院区”分别记录已验证能力，产品只开放实际通过验证的操作。

首批验收选择同一通用平台至少两家新增医院，建议北京大学人民医院与中国医学科学院肿瘤医院作为候选样本：本轮已读取两院官方指南，可覆盖不同放号、取号及取消规则。正式名单取决于后续实时目录和可用接入；宣武医院仍保留在后续候选中，本轮未核实其具体规则。佑安服务号作为回归样本。这里没有确定就诊日期、医生、患者或新增真实预约；测试不能为验证而制造无就医需求的预约。

## 2. 平台调研与方案选择

完整证据、来源 URL 和时间见 [北京平台调研](../../research/2026-09-25-beijing-platform-landscape.md)。主要事实对设计的约束如下：

| 证据 | 设计影响 |
| --- | --- |
| 北京 114 是多医院统一预约入口；医院官方指南仍列 114 网络/电话等预约方式 | 优先验证一个多医院平台，避免复制每家医院独立网站实现 |
| [北京市政府 2026-04-03 报道](https://www.beijing.gov.cn/fuwu/bmfw/sy/jrts/202604/t20260403_4573621.html)称统一平台以京通 App 为总入口，已覆盖全市二三级医院 | 明确统一平台具有扩展价值；该统计是报道口径，不能当作本 App 当前支持清单或实时目录实测 |
| 京通提供统一医疗服务入口；京医通原预约服务于 2023-04-24 下线，原公告指引医院官方渠道 | 入口品牌、用户身份、后台服务分别建模，不推断旧身份或接口已迁移，不沿用旧“京医通 API”推断现状 |
| 卫健委要求医院预约系统接入全市号源管理平台 | 属于医疗机构对接要求；不据此宣称个人 Android App 已有开放 API 使用资格 |
| 同院多渠道统一放号，医院之间仍有不同放号时刻和周期 | 每院/院区/科室保存规则、来源和核实时间，不写死全市统一时间 |
| 支付、取号、取消/退费存在院区和渠道差异 | 预约、付款、就诊准备分开保存；所有后续操作回到订单原渠道 |

本次技术观测：`https://www.114yygh.com/` 直接 HTTP 读取只得到浏览器校验脚本和空正文；内置浏览器也未显示业务页面。未获得医院目录、号源、认证或订单 API 的当前真实响应。通用阅读器读取超时，搜索服务部分请求失败；已读到的政府/医院正文与无法读取的技术来源分别记账。本次没有登录、发送验证码、提交挂号或付款。

续验增量：[京通官方专题](https://www.beijing.gov.cn/fuwu/bmfw/bmzt/jt/index.html)明确 App 与小程序共用用户体系；[官方帮助中心](https://portal.bjt.beijing.gov.cn/p/help/help.html?pubKey=null)的可见页面确认“京通 App 登录→扫一扫→手机确认→跳转业务”的通用认证流程。该事实不能延伸为与 114 共享医疗 Cookie、患者绑定或订单。114 续验返回 HTTP 202 校验壳；普通 Chrome 复核受工具认证能力限制，未进入页面。证据详见[京通验证记录](../../research/2026-09-25-jingtong-entry-verification.md)。

**未找到经本次验证、可直接用于第三方 App 的开放 API 文档，不等于平台没有内部接口。** 旧代码里的端点、公开网页可访问、机构间互联要求，都不能替代正常客户端认证与业务回读。

最新现场证据：用户微信截图显示同域名业务首页、个人中心和“共309家医院”，但该数值仅为页面展示，未枚举医院或读取 API。菜单没有复制链接入口，114 接入不得要求“复制微信页面链接导入”；佑安服务号的导入设计不外推到新平台。官网[第一方公告图片](https://img.114yygh.com/image/web-offline/cont.png)已从正常 Chrome 及独立下载双重目视核验，网站渠道已关闭。手机当前没有标准公开 WebView 调试 socket。用户已单独确认一次限定范围的本机 HTTPS 采样，本机通道与脱敏自测通过，尚待手机证书安装和实际接口响应；见[采样验证](../../research/2026-09-25-114-scoped-https-verification.md)。该采样仅用于可行性研究，不是产品的常规接入流程，也不据此认定独立认证或自动提交可用。

| 方案 | 优点 | 代价 | 决定 |
| --- | --- | --- | --- |
| 北京 114 优先＋保留佑安适配 | 与覆盖更多医院的目标直接对应；差异集中在适配器 | 当前协议、认证、自动提交资格仍需验证 | 推荐，作为目标设计；未验证功能默认关闭 |
| 逐院扩展服务号/互联网医院 | 可复用单院验证经验 | 每院重复认证和维护，覆盖扩展慢 | 仅作为确有需要的补充，不是 v0.2 主线 |
| 只整理官方链接和放号提醒 | 对接口依赖小 | 无法交付通用接口自动挂号 | 可作明确标注的降级能力，不能替代 v0.2 完整验收 |

## 3. 范围与成功条件

纳入设计：北京医院搜索与选择、同院可用渠道展示、平台独立认证、就诊人绑定核对、院区/科室/医生/日期/时段选择、按院放号规则、自动任务、订单核对、原渠道付款或到院取号说明，以及旧版数据迁移。

首批范围是普通门诊预约；急诊、发热门诊、肠道门诊、互联网门诊及基层转诊专属号源不混入这一流程。医院身份认证要求同时涉及实际就诊人和代预约人时，分别核对，不将账号持有人默认视为就诊人。

延续 v0.1：手机本地执行，目标设备 Mate 60 Pro / 鸿蒙 4.2.0；任务最长运行时长默认 30 分钟且可配置；同时最多一个自动执行任务；用户自行付款；提交结果未知时先核对，不重复提交；医保不可用时不自动改成全额支付。

本版不增加其他城市、云端抢号、多渠道竞速、多任务并发、多医生自动替换、自动付款/取消/退费、候补自动提交、验证码代解或风控绕过。新通用平台的医保初始化必须独立验证，不能照搬佑安的 `sxPayCN`。

设计完成与版本交付分开：本设计稿和调研是本任务产物；后续 v0.2 完整交付必须满足两家新增医院真实认证/查询、提交与同单回查证据、所需官方付款/取号交接、真机自动执行和 v0.1 回归。只完成目录或模拟运行时只能报告对应部分能力。

## 4. 用户流程与页面变化

主路径：选择医院 → 核对院区与渠道 → 连接平台 → 选择该平台就诊人 → 选择科室/医生/就诊时间 → 核对放号规则与费用 → 启用任务 → 查看挂号结果及下一步。

| 页面 | v0.2 行为与文案 |
| --- | --- |
| 医院选择（新增） | 搜索名称、区县；卡片展示医院/院区、可用渠道、能力说明。目录资料有来源与更新时间。搜索失败显示“暂时无法加载医院”，不能当成医院不存在 |
| 医院详情与渠道（新增） | 北京 114、已接入的医院服务号分别成行；显示“可创建自动挂号任务”“可查号，需到官方完成挂号”“仅提供官方入口”“暂不可用”等实际能力。协议 URL、状态码不进入用户流程 |
| 平台连接（扩展原接入页） | 展示官方认证步骤、会话状态、可用就诊人。姓名脱敏。验证码/实名核验由用户在官方支持的入口完成；只有服务端身份核对成功才显示已连接 |
| 新建任务（扩展） | 顶部固定医院、院区和渠道；切换任何一项即清空依赖的就诊人、科室、医生、号源和规则确认。放号日期与就诊日期分开显示，冲突需重新核对 |
| 启用确认（扩展） | 明示就诊条件、费用上限、支付偏好、放号时刻、运行截止、该院付款/取号要求。已确认的执行任务不在运行中静默换渠道 |
| 任务列表/详情（扩展） | 每项都带医院/院区/渠道。状态沿用“挂号任务”“自动挂号”；需要官方验证时解释影响和恢复条件 |
| 挂号记录/详情（扩展） | 展示原渠道、预约结果、付款状态、取号/就诊准备与真实截止时间。可打开已验证的官方入口；无法直达订单时明确给出人工路径 |
| 平台管理（新增） | 分平台查看连接、重新接入、删除本机会话。存在未决提交时先提示核对；删除会话不会删除医院订单 |

无需单独制作一套 v0.2 首页导航：复用 v0.1 任务、记录、设置结构。18 页 UI 源稿由 v0.1 任务维护，本稿定义页面增量与文案，不直接改源稿。

进入渠道选择时可推荐“该医院已通过完整验证且已连接”的渠道；最终由用户启用确认锁定。没有可自动挂号的渠道时，仍可提供官方入口，但不显示自动任务“已就绪”。京通与 114 是否共享号源、账号或订单不从同一医院名称推断。

## 5. 身份、医院与数据模型

以下为领域契约，不是平台真实字段名或已实现 Kotlin 类型。适配器负责解析原始响应，核心模块不认识各平台原始状态码。

| 对象 | 关键字段与不变量 |
| --- | --- |
| Provider / EntryPoint | Provider 表示经过验证的独立协议与身份域；EntryPoint 表示官网、微信服务号、小程序等入口。暂定本地键 `youan_psc`、`beijing_114`；京通先记入口，协议独立性实测后决定 Provider，不虚构远端 ID |
| HospitalRef | `providerId + remoteHospitalId`；院区使用远端 campusId，若平台给院区独立医院 ID 则保留该 ID。名称仅展示。没有可稳定区分的 ID 时不自动合并或提交 |
| HospitalIdentityMap | 可选的本地展示归并：一个实体医院关联多个 Provider HospitalRef；须人工或一手证据验证，不按同名/相似名自动合并；不授予跨平台身份能力 |
| AccountSession | `providerId + credentialScopeId + localAccountId + credentialVersion`，含入口、预约人身份验证状态、已核验认证等级、业务所需认证等级、验证时间/失效状态；等级未被业务验证则记未知，不能以通用门户登录代替。credentialScopeId 默认按入口隔离，只有证明医疗会话可互通才合并。机密凭据独立加密存储，禁止日志输出 |
| PatientBinding | `providerId + credentialScopeId + localAccountId + remotePatientId`，如平台要求再附 `HospitalRef + cardId`；同一个人不同渠道分别绑定。身份识别失败不可仅按姓名继续 |
| DepartmentRef / DoctorRef | 包含 HospitalRef 与远端科室/医生 ID；上级科室、院区、原始名称保留。目标指定医生但响应只有门诊类型时不能以同名替代 |
| ScheduleSlot | HospitalRef、科室/医生或门诊类型、就诊日期、时段 ID、时段范围、排班/号源 ID、价格、库存语义、响应时间；提交只使用本次服务端返回且经适配器验证的标识 |
| HospitalRules | 放号周期和时刻、例外日期、停止预约/取消时限、预约频次/爽约限制、取号规则、支付方式、来源 URL、核实时间、适用渠道/院区/科室/门诊类型/就诊人类型、版本；未知字段明确 null/unknown |
| BookingTask | 固定 provider/hospital/campus/patient/condition、规则版本、放号时刻、运行时长、费用上限、支付偏好、generation；一旦启用，不能原地换渠道 |
| SubmissionAttempt | 任务和身份版本、原始候选引用、提交时刻、此前订单基线、平台 requestId（若有）、核对状态；先持久化再发请求 |
| OrderRef / Snapshot | `providerId + credentialScopeId + localAccountId + HospitalRef + remoteOrderId` 作为本地关联键，另存原始入口；含 PatientBinding、就诊条件、原始状态、预约/付款/履约状态和服务端截止时间；不把不同平台或未经证实互通的入口同号订单合并 |

库存用 `AVAILABLE_WITH_COUNT / AVAILABLE_WITHOUT_COUNT / NONE / WAITLIST / UNKNOWN` 区分；没有数量不伪造“余 1”，缺字段或读取失败不转换成无号。价格以人民币分保存，缺失价格不能当作零元；不能核对费用上限时禁止自动提交。

静态目录可以缓存并标明更新时间。排班缓存仅用于浏览，自动提交前须获取新响应并复核条件；库存没有可承诺的有效期。放号规则若缺失，可由用户填写明确的北京时间并标为用户提供；已发现规则冲突时必须核对，不能以手填覆盖已知限制。具体医院时间见调研，不内置“全城 8 点/7 天”。

规则同时保留原始文本与结构化值。“前一工作日”依赖适用节假日和调休规则，不可简化为减 24 小时；无法可靠计算时只展示官方原文并引导核对。停诊、替诊、补诊、候补分别保留，指定医生发生变化时通知用户决定，不能因停诊自动宣称取消或接受替诊。

## 6. 能力与接口契约

能力按 `Provider + HospitalRef + EntryPoint` 独立保存，具备范围、证据版本、最后验证时间和可用状态。认证成功不自动解锁所有能力；目录发现不自动开通提交。

| 能力端口 | 输入/输出契约 | 对北京 114 的当前证据 |
| --- | --- | --- |
| Catalog.listHospitals / departments | 分页游标、筛选 → 远端稳定 ID、名称、院区、完整性/下一页 | 官方多医院渠道有来源；实际 API 路径、方法、分页响应未验证 |
| Session.connect / validate | 官方支持的用户交互 → 独立会话及服务端身份核对 | 首次认证、会话寿命、Android 获取与续期未验证 |
| Patients.list / validateBinding | 平台会话及医院 → 已绑定就诊人和必需就诊卡 | 具体字段、跨院是否需建卡未验证 |
| Availability.query | HospitalRef、科室、日期 → 排班/医生/时段、库存/价格、数据时间 | 当前协议与分时余号响应未验证 |
| Booking.preflight | 固定任务＋候选 → 可提交、需用户验证、规则拒绝或未知 | 验证码/实名/风控触发时机未验证 |
| Booking.submitOnce | 持久化尝试＋固定候选 → 订单已找到、已接受待查、明确未受理、需交互或结果未知 | 端点、提交语义、幂等及防重复规则未验证 |
| Orders.reconcile / get | 尝试上下文、订单键 → 唯一同单快照或明确待核对 | 无订单号恢复与结果终态未验证 |
| Fulfillment.nextAction | 同单快照＋医院规则＋支付偏好 → 官方缴费、到院取号、已完成或需核对 | 官方医院流程有资料；App 同单交接未验证 |

所有端口统一区分 `AuthRequired / UserVerificationRequired / RateLimited(retryAfter) / TransportFailure / RulesChanged / Unsupported / MalformedResponse`。未知原始状态进入待核对，保留脱敏诊断。查询端点可以退避；提交端点、付款准备端点关闭透明重试。只有服务端明确未受理且适配器证据能证明未生成订单，才允许后续候选尝试。

本设计不填写猜测的 HTTP 路径、签名算法或验证码参数。实施前每个真实端点必须登记：官方来源、方法/路径、认证方式、请求/响应脱敏样例、成功/空结果/失效/限流/异常语义、可重试性、核验日期与证据文件。识别端点不等于通过接入验收。

## 7. 架构与 v0.1 衔接

[可交互架构图](../../../design/v0.2/beijing-platform-architecture.html) · [可编辑 JSON 源文件](../../../design/v0.2/beijing-platform.architecture.json)。图中实线是设计调用关系，非线上接口已打通证明。

- **页面层**：医院/渠道选择、任务条件与订单呈现；不拼接平台请求、不解析原始订单码。
- **核心执行层**：候选匹配、到期/停止、单次提交、未决核对、能力检查；复用 v0.1 的有限运行状态机。自动执行仍由 v0.1 Android 定时唤醒、前台服务和本地通知驱动。
- **平台注册与路由**：按任务固定的 providerId 选择适配器，按医院能力过滤操作；无远程脚本、无运行时下载插件。
- **佑安适配器**：继续封装现有服务号认证、号源、订单与医保状态映射。平台专用字段作为不透明内部数据，不提升成所有平台必填字段。
- **北京 114 适配器**：实现经实测确认的端口；不支持的能力显式返回 Unsupported。京通只有在独立验证后复用或另增适配器。
- **本机存储**：扩展任务、凭据、医院规则、能力证据和提交记录。Cookie jar、HTTP 会话和凭据分 provider/credentialScope/account 隔离；同品牌入口不自动共享。
- **官方后续操作**：仅打开验证过的 HTTPS 域名/官方 App 入口或展示准确路径；支付、取消和退费交还用户。

现有计划中的 `Channel.PSC_SERVICE_ACCOUNT`、`PatientRef(sessionId, patientId)`、`BookingGateway.lock/querySubmission` 等不能直接假定为跨平台协议。v0.2 在实际 v0.1 交付基础上增加包含平台与医院范围的引用，通过适配层映射旧字段；旧原始 `source/status` 仅供佑安适配器解码。

## 8. 执行、认证与恢复规则

1. 启用时检查医院支持能力、官方规则、会话/就诊卡、费用、通知和设备条件。`AUTO_SUBMIT` 只有在认证、只读链路、单次提交与同单恢复均通过验证后开放。
2. 放号前进行尽力而为的会话/规则检查；放号后串行查询。沿用 v0.1 至少 5 秒查询间隔作为本地保守起点，若平台要求更慢则服从平台；未验证频率不宣称允许。收到 429/限流按服务端等待时间退避。
3. 选定候选后再核对平台、医院、院区、就诊人、科室/医生、日期时段、费用与规则版本。已有同条件有效订单时暂停并提示核对。跨平台无法可靠去重时明确能力边界，不声称防止用户在其它客户端重复预约。
4. 持久化提交意图、基线和唯一尝试记录后发送一次。平台接受请求只进入核对；取得订单需精确确认属于同一身份与就诊条件。
5. 提交超时、连接断开、进程重启或登录失效都保留尝试记录。已知订单号直接查同单；无号时用基线和平台正式查询语义核对。列表为空、查询失败、订单暂未出现均不能证明提交失败。
6. 需要验证码/实名/设备核验时暂停自动动作，引导用户到官方支持的流程。若挑战发生于提交后或不能证明未提交，先核对订单；不能同时让自动任务和官方页面各提交一次。
7. 重新连接后核对仍是原平台、原账号与原就诊人。未决提交只恢复查询；更换身份不能接管旧任务。恢复不重置原放号时间或运行截止，错过截止不继续新提交。
8. 停止/到期阻止新提交，但已发请求仍有限核对。适配器须定义经验证的核对终态和时间预算；无证据前沿用 v0.1 最多自动核对 120 秒的本地上限，超出后显示“结果待核对”，不得报未挂上。

平台安全验证无法通过官方支持的用户交互完成，或正常客户端无法取得独立会话时，该渠道保持“需官方完成/暂不可用”。不读取微信或其它 App 私有存储，不关闭 TLS 验证，不复用他人凭据。

## 9. 订单、支付与就诊准备

预约结果、付款与就诊准备是三个维度，不沿用单院状态码覆盖全部情况：

| 维度 | 规范化结果举例 |
| --- | --- |
| 预约 | 处理中、已预约、明确未成功、已取消、已失效、未知 |
| 付款 | 待线上支付、支付中、已付、到院支付、无需支付、未知 |
| 就诊准备 | 无额外步骤、需取号、需实名/建卡补充、需官方确认、未知 |

| 已核对的平台事实 | App 展示与动作 |
| --- | --- |
| 有明确有效订单，支付是完成预约的必要条件 | “锁号成功，待付款”；显示服务端付款截止，用户到原渠道支付 |
| 预约已成立，需要到院缴费/取号 | “预约成功，待到院取号/缴费”；展示院区、凭证与取号截止，不错误显示待线上支付或已支付 |
| 预约已成立且所需线上支付已确认 | “挂号已完成”；就诊准备仍可提示到院取号 |
| 接受处理但未确认订单 | “正在核对挂号结果”；不显示成功 |
| 仅知道可能是候补或未知订单码 | “需到官方核对”；候补不当成正式预约 |

同一订单的付款期限、取消期限、取号期限分别保存，均不等于任务运行时长。未知期限直接标明“请到官方核对”，不填默认 30 分钟；医院临时公告与订单信息冲突时保留原文并提示确认。

医保偏好延续 v0.1：平台明确支持时提供已验证的官方医保流程；仅支持到院支付时展示医院规则；医保不可用或能力未知时要求用户决定，不替换为全额支付。不因为用户打开/返回官方页面就更新订单成功，返回后必须同单读取；不具备读取能力时只显示“待确认”。取消、退款和付款均坚持原渠道，不调用另一渠道的同名订单接口。

## 10. 数据迁移与回滚设计

迁移以 v0.1 最终数据库/模型为输入，实施时明确 schema 版本和迁移脚本；本稿不假定当前已有数据库版本号。旧任务、订单、就诊人与会话全部显式映射为佑安服务号，保留原 ID、凭据、状态、generation 和未决尝试。

应用升级时先取得执行锁、停止新调度。若存在未决提交，必须在保留全部原始尝试字段的前提下迁移，并优先由佑安适配器恢复只读核对；迁移不能重置成可提交状态。旧活动任务保持暂停/待复核，用户重新启用前核对医院映射与既有截止，不能静默续跑。没有未决记录的历史只做字段补全，不伪造支付或渠道验证证据。

迁移在事务中进行；失败保留旧数据库并停止任务，不能回退为空库。迁移前备份位于 App 私有目录，凭据仍受原 Keystore 密钥保护，不输出为明文备份。迁移后数据计数、订单键、状态和尝试记录逐项校验。

功能回滚优先关闭新平台能力，保留订单读取和人工处理入口。不能直接安装旧 APK 覆盖新 schema；涉及已有新订单的数据回退应采用兼容修复版本，或在核对全部未决订单后采用明确的备份恢复流程。任何回滚都不自动取消医院订单。

本次仅修改独立设计、研究材料及索引。文档可通过恢复修改前索引和移除本次新增文件回滚；已提交后优先使用单独的 `git revert` 提交，不改写远端历史。

## 11. 后续验证条件与验收矩阵

验证顺序服务于实现可行性，不是本任务的开发排期。先取得真实认证和查询证据，再开放自动提交。接入发现协议不可用时，记录为技术阻塞，不能把“官方入口可打开”当作接口支持完成。

| 验证项 | 通过标准 |
| --- | --- |
| 平台覆盖 | 同平台两家新增医院及院区从当前目录读取；ID、名称、科室可稳定解析；分页/空结果/失败语义区分清楚 |
| 正常认证 | Android 经官方支持入口首次接入；服务器核对用户与就诊人；失效后可恢复；全过程无私有数据提取 |
| 医院差异 | 两院放号/预约周期/取号或支付规则分别核对，含变更和临时停诊；不同院区不混用 |
| 会话隔离 | 平台同名患者、不同账号同号患者、两院相同科室/医生 ID 均不能串用；京通与 114 未验证前不互换凭据 |
| 号源与费用 | 模拟有数量/无数量/无号/未知/候补/缺价/费用超限；不能误提交；真实只读响应与官方页面对应 |
| 单次提交 | 本地模拟医院已受理但响应丢失、重复唤醒、重启、用户停止；发送计数仍为一次，先持久化再发送 |
| 同单回查 | 精确订单关联；用户在官方另下订单也不误认；无号、列表延迟、登录失效或未知状态不触发第二次提交 |
| 验证码与限流 | 正常触发暂停/退避；挑战后先核对再决定下一步；任务截止不延长 |
| 支付与取号 | 分别覆盖待付、已预约到院付、无需付款和未知；同单状态回读与官方一致，不强制要求所有医院支持医保 |
| 真机执行 | 两院查询通路在 Mate 60 Pro 验证定时、锁屏、断网恢复与通知；复用 v0.1 设备机制但独立记录平台结果 |
| 旧版兼容 | 佑安普通/医保映射、旧任务、凭据和未决记录迁移回归通过，原渠道仍可用 |
| 发布口径 | 分别报告目录医院数、可查号医院数、可自动挂号医院数与日期；至少两家新增医院达到完整自动任务链路才称 v0.2 目标达成 |

所有自动化测试使用合成患者、号源和订单，不保存真实身份或医疗信息到仓库。真实提交验证使用用户安排的实际就医需求及明确条件；若暂缺需求，相应验收保持未执行，版本不能宣称该项已通过。

## 12. 决策记录与待验证事实

已确定的设计取舍：北京 114 优先；京通单独核验；适配层统一、医院规则独立；渠道固定到任务；单任务串行执行；能力由证据开放；预约/付款/取号分离；先兼容 v0.1 再扩展。

待验证事实及处理：114 正常客户端接口和认证（未通过则不开自动任务）；京通与 114 的协议/医疗会话关系、京通各入口医疗会话关系（共用产品用户体系已知，业务会话未证实则隔离）；首批医院实时目录、就诊卡要求、放号与支付语义（逐院核对）；异常提交恢复（不能唯一核对则人工处理）；v0.1 最终代码与 schema（开发开始前重读并制定迁移）。这些是明确的验证任务，不用假设填补。

本设计不包含实现步骤级开发计划，也不创建 Android 工程。用户评审后，可在后续任务基于实际 v0.1 交付版本制定开发计划。
