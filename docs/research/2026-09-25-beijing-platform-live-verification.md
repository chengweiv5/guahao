# 北京统一预约平台：正常入口续验

验证日期：2026-09-25。状态：**完成本轮公开入口检查，医疗业务接口验证受阻，等待手机官方入口。**

用户已要求 v0.2 仅保留本地，本轮不推送；继续验证服务于设计，不进入 Android 实现，不发起真实挂号。前次[平台调研](2026-09-25-beijing-platform-landscape.md)与本次[京通入口验证](2026-09-25-jingtong-entry-verification.md)分别记录业务覆盖和技术访问证据。

114 校验脚本没有被反混淆、执行重放或用于绕过限制。二维码识别最初的 Vision 引擎失败（本机 ANE 模型加载问题），随后用宿主 CPU 解码成功；与平台访问结果分开记录。没有通过增加请求频率或更换身份尝试避开校验。

本轮阻塞是**缺少可进入的医疗业务客户端上下文**：114 桌面停在校验响应，普通 Chrome 工具未能启动，京通公开页面没有医疗直链。没有授权拒绝或证据表明平台整体不可用；也没有可以后台轮询的真实授权流程。不要生成猜测的 clientId/回调地址或拿通用身份二维码充当医疗认证。

## 下一步用户配合

优先在手机微信打开“北京114预约挂号→挂号”，正常登录后使用页面菜单复制官方页面链接；如果不支持复制，记录停在哪一页。也可从“京通→健康服务”提供正常入口。只需要入口和页面阶段，不需要把验证码、密码、身份证等资料发到对话。

收到真实入口后：先核对域名与官方来源；若含认证参数，在本地临时凭据边界内处理、不写入仓库/通知；仅进行用户授权的会话有效性、医院/科室/排班及所需就诊人绑定只读验证。遇到新的人机验证或实名认证，让用户在官方客户端正常完成。未获得本次真实挂号条件前不提交订单。

## 对设计的修正

1. App 与小程序共用用户体系不再列为完全未知；医疗会话、订单、支付和 114 的互通仍保持独立验证。
2. 认证模型增加“已核验的认证等级、该业务要求的等级、核验来源/时间”，不能只有 `loggedIn=true`。
3. 网页 HTTP 状态、正常客户端可达性、匿名查询、医疗会话、自动提交能力分别记录，不能层层自动推定。
4. “官方入口可用”目前只指已读到官方说明与路径，不表示 APK 可以直达医院订单，也不表示本项目可自动挂号。

脱敏观测摘要见 [入口验证证据](evidence/2026-09-25-beijing/entry-verification.json)。原始 HTML、响应头与临时二维码仅保存在 `/tmp/guahao-v02-live-20260925/`；响应头等原始材料不纳入版本管理。后续用户入口可能含会话参数，亦不得纳入证据提交。
