# 佑安服务号：医保支付分支核对

## 结论

官方流程可以选择“医保移动支付”，选择发生在锁号成功之后。`lockRegis` 的前端请求没有支付方式字段；不能通过自行添加 `isyb` 或 `paytype` 来宣称已选医保。

用户要求优先医保支付。此次只读取官方页面、功能校验和订单状态，没有新锁号、初始化支付、付款、取消或退款。当前没有待付款订单；此前验证订单已是“已预约”，不能在该单上验证待付医保选择。

## 官方流程与证据

1. `POST /regis/lockRegis` 仅提交身份、医生日期时段等；`queryRegisStat` 成功后处理付款分支。先区分零元、候补、献血优惠及功能限制。
2. `POST /function/functionControl` 使用 `functionid=001`。本次返回 `code=0`，仅说明医保功能开放，不等于个人医保资格或订单结算通过。
3. 排班页选择医保时调用 `POST /order/sxPayCN`，字段为 `userId,userIdKey,orderNo`。本轮未调用这个业务写接口。
4. 成功后将响应 `data` 保存到 `sessionStorage.pathUrl`，进入 `/regis/regisYbPayState`，参数 `paytype=1`。代码注释指向医保小程序授权；实际手机接续、授权和结算待验。不带订单读取交接模板未成功，未使用已完成订单试探。
5. 结果列表的 `sendPay()` 检查期限及献血优惠后直接进入 `/order/regisOrderSend`，没有医保选择，也不按 `isyb` 分流。这与排班页“全额支付”入口相同。

因此，先前“锁号 → 通知 → 挂号结果查询 → 缴费”的验证不能涵盖医保流程。结果页省略医保选择，能够解释用户从该入口无法选择医保的现象。尚不能证明先调用 `sxPayCN` 后，结果页会自动接回医保；下游入口对医保初始化订单的行为没有实测。

## 本次订单检查

只读列表检查没有可用于本次医保初始化验证的锁号待付订单（`status=1/7`）。公开记录不保留个人订单数量、其他订单状态、患者姓名、订单号或身份参数。独立支付流水未取得，单个医保标记或空分摊字段不能作为医保结算结果证明。

## 需求修正与待验证项

- 支付偏好按用户要求优先“医保移动支付”；医保不支持或失败时提示，不自行转为全额支付。
- 取得订单后先停止查号，再按支付偏好准备官方付款交接；医保初始化与用户授权/付款分别记录，不能以初始化成功代替医保结算完成。
- 需验证：锁号后初始化 → 手机微信接续官方医保小程序 → 用户授权付款 → 同一订单状态及结算结果核对。
- 保留零元、候补、特殊医保类别与献血优惠分支；不替用户放弃优惠，不伪造医保资格。
- 跨设备的 `sessionStorage.pathUrl` 不会因手机打开结果列表自动传递。可恢复的官方手机入口尚未验证，不能承诺“锁号时选医保，稍后从结果列表一定能医保支付”。
- 后续真实试验需要一笔用户明确安排的有效待付款单。本次不新增预约、不变更已完成预约，继续暂停 Android 开发。
